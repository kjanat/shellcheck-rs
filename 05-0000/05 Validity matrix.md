# 5 Validity matrix

The differential gate proves `rshellcheck` equals ShellCheck. The validity matrix proves a diagnostic's claim by running its reproducer in real shells, one container per shell and version. `docs/validity.md` is the design document.

## 5.1 Files

| Path                               | Holds                                                                         |
| ---------------------------------- | ----------------------------------------------------------------------------- |
| `validity/sources.toml`            | Hand-written: per shell, how to fetch it and which versions.                  |
| `validity/matrix.toml`             | Generated by `cargo validity pin`: every cell with its pins and image digest. |
| `validity/specs/SC<code>.toml`     | One spec per diagnostic: snippet, fixed script, claim, observable.            |
| `validity/outcomes.toml`           | Generated by `cargo validity --record`: outcome per spec per cell.            |
| `validity/REPORT.md`               | Generated with the outcomes: per code, where it reproduces and where not.     |
| `docker/shells/<shell>/Dockerfile` | Builds one interpreter from the pinned source. `fetch.sh` verifies the pin.   |

The first four shells are `shipped = true`: `rshellcheck` has a `--shell` value for them. A cell with a `dialect` runs the `rshellcheck` assertions with that dialect. The BSD shells run inside guest operating systems under QEMU. Their source is a disk image URL with its SHA-256. tcsh has an unrelated grammar and normally records `unparsable`.

A tarball is fixed by its URL and SHA-256, a git source by repository, tag and resolved commit, a crate by its crates.io version. `cargo validity pin` resolves every version, keeps entries already in `matrix.toml`, resolves the base image to a digest and asks the registry for each image's digest. `pin --refresh` re-resolves git tags and base digests.

## 5.3 Specs and outcomes

A spec holds a `code`, a `claim`, a `[snippet]` script, a `[fixed]` script and one or more `[observe]` blocks of kind `stdout`, `status` or `stderr-contains`. Scripts read stdin and finish in under a second. The root is read-only; `/tmp` is a 16 MiB tmpfs; each run starts in a fresh `TMPDIR` directory.

Per spec per cell the runner asserts:

1. The shell parses both scripts.
2. The snippet produces `observe.snippet`.
3. The fixed script produces `observe.fixed`.
4. On a cell with `dialect`: `rshellcheck` reports `code` on the snippet.
5. On the same cells: no `code` finding appears on the fix.

| Outcome      | Meaning                                                             |
| ------------ | ------------------------------------------------------------------- |
| `reproduces` | Assertions 1 to 3 hold.                                             |
| `absent`     | Both scripts produce the fixed observable. The shell lacks the bug. |
| `differs`    | Some other output, recorded verbatim.                               |
| `unparsable` | The shell rejects the snippet or the fix.                           |
| `timeout`    | Exceeded the per-run limit.                                         |
| `port-miss`  | Assertion 4 or 5 failed.                                            |
| `missing`    | The cell has neither a reachable digest nor a local build.          |

Gate: on a shipped cell any change from `reproduces` fails, and `port-miss` fails. On an unshipped cell changes are reported and the run passes; the recorded outcome is the rule the dialect will ship with. A spec with no `reproduces` cell at all fails.

Specs at `master`: SC2016, SC2046, SC2086, SC2164, SC3010. `REPORT.md` records, among others, that SC2086 is `absent` on zsh 5.8.1 and 5.9 in native mode and `reproduces` under `emulate sh`, and that SC3010 reproduces on the POSIX-only shells (dash, posh, bosh, FreeBSD and NetBSD sh) and is `absent` everywhere `[[` exists.

## 5.4 Runner

```sh
cargo validity [--record] [--cell <shell>[:<version>]] [--code <n>]
cargo validity build [--push] [--cell <shell>:<version>]
cargo validity pin [--refresh]
cargo validity cells
```

The runner reuses one isolated container per cell: scripts on stdin, a five-second limit, no mounts, no network, no Linux capabilities, read-only filesystem apart from the temporary directory, `LC_ALL=C`, `TZ=UTC`, `HOME=/tmp`, an environment holding only `PATH`. It pulls by the digest in `matrix.toml`, falls back to a local build of the cell's tag when the digest is unreachable, and records `missing` otherwise. Parsing uses the shell's `-n` where it has one. Spec execution order is sorted by code then cell. Output is deterministic byte for byte. A host without Docker fails with one message. Fuzz scripts are never executed; only curated specs run.

## 5.5 Images and the workflow

Image name: `ghcr.io/kjanat/shellcheck-rs/shell-<shell>:<version>`. `shells.yml` builds them:

- `pin` runs `cargo validity pin`, then selects the cells to rebuild with `tools/affected_shell_cells.py` against the comparison commit, or every cell on `rebuild-all`.
- `build` runs once per selected cell. On pull requests it builds locally; otherwise it runs `cargo validity build --push`, attests build provenance with `actions/attest-build-provenance`, generates an SPDX SBOM with Syft and attests it.
- `run` opens `/dev/kvm` for the VM cells, resolves digests, runs `cargo validity --record`, and when `matrix.toml`, `outcomes.toml` or `REPORT.md` changed, commits them on branch `validity/drift` and pushes it for a pull request titled "Record shell validity drift". That branch is excluded from the workflow's own triggers.

Verify an image:

```sh
gh attestation verify oci://ghcr.io/kjanat/shellcheck-rs/shell-bash:5.3 --owner kjanat
gh attestation verify oci://ghcr.io/kjanat/shellcheck-rs/shell-bash:5.3 --owner kjanat \
  --predicate-type https://spdx.dev/Document/v2.3
```

`rust.yml` adds a `validity-smoke` job that builds and runs the `bash:5.3` and `dash:0.5.13` cells on every conformance run.

## 5.6 Relation to upstream and to dialects

ShellCheck's five shells (sh, bash, dash, ksh, busybox) are the floor. For floor cells the reference binary's verdict on the snippet is recorded as `oracle = "reports" | "silent"`. Where `rshellcheck` reports and the Haskell binary stays silent, the spec is the evidence a sanctioned deviation needs. A rule about any other dialect is proven by executing it in that shell at each version. Added dialects and their codes belong to this project and are documented in `docs/diagnostics.md`.
